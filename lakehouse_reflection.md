#  My Lakehouse Reflection
I created a mini lakehouse to store student engagement data from September, October, and November 2024. I organized the CSV files into folders based on the year and month to make the data easier to find and manage. This helped me understand how partitions are used to organize data in a lakehouse. I used DuckDB to query the data, calculate the average duration for each event type, filter events by type and campus, and count the number of events at each campus. I also learned how selecting a specific month can help limit the amount of data being read. The metadata files describe the columns, data types, and partition keys, which makes it easier to understand how the data is organized and what each file contains. I also created a second schema version with an optional advisor_note column to show how the data can change over time. The older CSV files can stay the same even when a new column is added, so there is no need to change every existing file. I learned that a lakehouse can store data in files while still allowing tools like DuckDB to query and analyze it, which is one difference between a lakehouse and a traditional data warehouse. In larger systems, tools and formats like Delta Lake, Apache Iceberg, and Apache Hudi can help manage changes and keep data reliable, including through support for ACID transactions. Overall, this mini lakehouse helped me understand how partitions, metadata, and SQL queries work together to organize and analyze data in a lakehouse.
